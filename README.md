# ScamTrainer

Тренажёр против мошенников: пользователь ведёт диалог со сценарным LLM-агентом,
его решения оценивает движок сценариев, итог попадает в профиль и лидерборд.

## О проекте

ScamTrainer учит распознавать схемы обмана на классифайд-площадке, давая безопасно
прожить их изнутри. Пользователь выбирает сценарий и оказывается в чате, где собеседник —
LLM-агент, играющий мошенника. Агент не импровизирует свободно: он движется по графу обмана,
который автор сценария описал в YAML, и через tool-calls отмечает, на каком шаге пользователь
повёлся. Сценарии бывают составными — сначала прогрев доверия, потом увод на фишинг.

Каждый переход по графу несёт вес `score_delta` и текстовый разбор `feedback`: опасный выбор
уводит счёт в минус, осторожный — в плюс. Дойдя до вершины-концовки, чат закрывается, накопленный
балл один раз начисляется в профиль пользователя и поднимает его в общем лидерборде.

Сквозной путь: регистрация и вход по JWT → создание профиля → каталог сценариев → создание чата
с детерминированной первой репликой → диалог с DeepSeek → продвижение по графу → завершение
и начисление очков.

Отправка сообщения отвечает `202` сразу, а реплика агента и результаты решений приходят клиенту
в SSE-поток — LLM отвечает секундами, держать на этом синхронный запрос нельзя.

Проект сделан на хакатоне Avito; постановка домена чатов — их же.

**Раскладка неоднородна и это осознанно.** `chat` и `users` разложены по слоям
domain / usecase / transport / repository, а `auth`, `training`, `middleware` — плоские пакеты.
Так вышло из решения не переписывать чужие пакеты при слиянии веток; зафиксировано
в `backend/docs/chat.md`, §6.

Границы доменов внутри монолита — организационные и компиляционные, а не сетевые: домены
вызывают друг друга напрямую, как Go-код, через узкие интерфейсы. Никакого HTTP, gRPC
или очередей между ними нет, конкретные реализации связываются в `cmd/app/main.go`.

## Разграничение доменов

Три предметных домена. Общий принцип: **сценарий знает про граф, но не про пользователя;
чат знает про диалог, но не про правила оценки; пользователь знает про баллы, но не про чаты.**

| | Сценарии | Чаты | Пользователи |
|---|---|---|---|
| Предмет | граф обмана и правила движения по нему | диалог, история, общение с LLM | личность, профиль, счёт |
| Состояние | read-only каталог в памяти + сессии тренировки | `chats`, `messages`, `chat_decisions` | `auth.users`, `users_schema.users`, `user_progress` |
| Хранилище | YAML-файлы | PostgreSQL | PostgreSQL |
| Кто источник правды | веса переходов, тексты, промпты | ход диалога, накопленный балл чата | суммарный счёт и место в рейтинге |
| Знает про соседей | ни про кого | про всех троих | ни про кого |

Зависимости однонаправленные: **чат — единственный домен, который знает соседей**. Сценарии
и пользователи друг о друге не подозревают и в чат не смотрят. Поэтому граф зависимостей —
дерево без циклов, а не клубок:

```
        transport/rest/chat
                │
        usecase/chat  ─────────┬──────────────┬───────────────┐
                │              │              │               │
        domain/chat      training +     usecase/users    agent (deepseek)
        repository/pg    domain/scenario  (ScoreAwarder)
                         repository/yaml
```

Каждый домен ниже описан отдельно: что он решает, из чего состоит, как работает,
что требует от соседей и что отдаёт наружу.

## Домен сценариев

`internal/domain/scenario` · `internal/repository/yaml/scenario` ·
`internal/transport/rest/scenarios` · `internal/training`

### Зачем он

Описать обман как данные, а не как код. Автор сценария — не обязательно программист: он пишет
YAML с репликами, вариантами поведения жертвы и ценой каждого варианта. Всё остальное — движок,
чат, LLM — этот файл только исполняет. Добавить новую схему обмана значит положить файл
в `backend/scenarios`, а не написать ветку в коде.

### Модель

Сценарий — направленный ациклический граф:

| Сущность | Поля | Смысл |
|---|---|---|
| `Scenario` | `id`, `title`, `role`, `difficulty`, `start_node_id`, `llm.character_prompt`, `nodes` | схема обмана целиком |
| `Node` | `type`, `message`, `llm.reply_instruction`, `transitions`, `outcome` | точка сценария |
| `Transition` | `id`, `description`, `examples`, `to_node_id`, `score_delta`, `feedback`, `risk_tags` | вариант поведения пользователя и его цена |
| `TrainingSession` | `id`, `user_id`, `scenario_id`, `current_node_id`, `status`, `score` | где именно находится конкретное прохождение |

`role` — чью сторону играет пользователь: `buyer` или `seller`. `difficulty` — `0` / `1` / `2`
(easy / medium / hard). `type` вершины — `decision` (есть переходы) или `ending` (концовка,
переходов быть не должно).

Промптов два уровня: `character_prompt` описывает персонажа на весь сценарий,
`reply_instruction` — что агент делает именно в этой вершине. Чат склеивает их в system-промпт
вместе с текстом реплики текущей вершины.

Сейчас в каталоге четыре сценария:

| id | Сценарий | Роль | Сложность |
|---|---|---|---|
| 1 | Поддельная ссылка на доставку | seller | 0 |
| 2 | Покупатель с доставкой и нарастающим давлением | seller | 1 |
| 3 | Продавец просит задаток за бронь | buyer | 0 |
| 4 | Товар ниже рынка и «своя» служба доставки | buyer | 1 |

### Как работает

`Engine` — чистый и без состояния, ни БД, ни LLM он не знает:

- `Start(scenario, sessionID, userID)` — создаёт сессию на стартовой вершине с нулевым счётом.
- `ApplyChoice(scenario, session, transitionID)` — проверяет, что сессия жива, что переход есть
  у текущей вершины и что целевая вершина существует; сдвигает `current_node_id`, прибавляет
  `score_delta` и возвращает `Decision`. Если целевая вершина — `ending`, сессия помечается
  завершённой.

`TrainingService` — обвязка над движком: достаёт сценарий из репозитория, генерирует `session_id`,
сохраняет сессию и отдаёт наружу `StartResult` (сессия, стартовая вершина, `character_prompt`)
и `TurnResult` (сессия, новая вершина, решение, признак завершения).

### Особенности и решения

- **Загрузка один раз при старте.** `NewYAMLRepository` читает директорию `SCENARIOS_DIR`
  и держит сценарии в `map[int]*Scenario`. Это read-only каталог, а не изменяемое состояние,
  поэтому синхронизация не нужна. Дубль `id` между файлами роняет старт приложения.
- **Валидация строгая и на входе.** Проверяются поля (положительный `id`, непустой заголовок,
  известная роль и сложность, существование стартовой вершины), вершины (известный тип,
  у `ending` нет переходов, у `decision` они есть, `id` переходов уникальны, цели существуют),
  а затем граф обходится DFS: **цикл или вершина, недостижимая из стартовой, — ошибка загрузки**.
  Битый сценарий не доедет до пользователя, он не даст приложению подняться.
- **Ацикличность не формальность.** Цикл в графе означал бы бесконечную тренировку без концовки
  и без начисления очков.
- **Числовой `id` живёт в самом YAML.** Отдельного маппинга между строковым и числовым
  идентификатором нет — то, что написано в файле, то и приходит в `POST /v1/chats`.
- **Сессии тренировки — in-memory** (`training.InMemorySessionRepository`). Рестарт их теряет;
  живыми чаты остаются за счёт регидратации на стороне чата. Цена — горизонтальное
  масштабирование потребует Postgres-репозитория сессий.
- **Два интерфейса вместо одного.** `ScenarioRepository.GetById` отдаёт весь граф — это нужно
  чату и training. `ScenarioCatalog` (`List` / `ListByDifficulty`) отдаёт только метаданные
  `ScenarioInfo`, потому что клиенту в каталоге граф обмана показывать нельзя: это спойлер.
  Обе роли реализует один `YAMLRepository`.

### Контракты

**Требует:** ничего. Домен не зависит ни от одного соседа — только stdlib и `yaml.v3`.

**Отдаёт:** `ScenarioRepository`, `ScenarioCatalog`, типы `Scenario` / `Node` / `Transition` /
`TrainingSession` / `Decision`, движок `Engine` и `TrainingService.Start` / `ApplyChoice`.

**HTTP:** `GET /v1/scenarios`, опционально `?difficulty=0|1|2`. Отдаёт только метаданные.
Нераспознанное значение — `400`.

## Домен чатов

`internal/domain/chat` · `internal/usecase/chat` · `internal/transport/rest/chat` ·
`internal/repository/postgres/chat` · `internal/eventbus` · `internal/agent`

### Зачем он

Свести вместе всё остальное: держать диалог и его историю, разговаривать с LLM, переводить
свободный текст пользователя в конкретный переход по графу и зеркалить результат в свои таблицы.
Это единственный домен, который знает про всех соседей.

### Модель

| Таблица | Ключевые поля |
|---|---|
| `chats` | `user_id`, `scenario_id`, `session_id`, `title`, `status`, `resume`, `score`, `current_node_id`, `created_at`, `finished_at` |
| `messages` | `chat_id`, `sender_type` (`agent` / `user`), `content`, `created_at` |
| `chat_decisions` | `chat_id`, `node_id`, `transition_id`, `target_node_id`, `score_delta`, `feedback`, `created_at` |

`status` — `active` / `finished` / `abandoned`. Ограничения домена: заголовок до 200 рун,
сообщение до 4000 рун — считаются рунами, а не байтами.

Переходы состояния живут в самом типе `Chat`, а не в юзкейсе: `ApplyDecision`, `Finish`
и `Abandon` каждый начинают с проверки `IsActive()` и возвращают `ErrChatFinished`. Закрытый
чат нельзя сдвинуть по графу мимо репозитория.

### Ход агента

```
POST /chats/{id}/messages
  ├─ валидация, запись реплики пользователя, событие message
  └─ 202 Accepted ──► горутина: RunAgentTurn
                        turnGate.acquire(chatID)      один ход на чат
                        chat.IsActive()               иначе выход
                        история: последние 50 реплик, курсором
                        system-промпт: character_prompt + reply_instruction + текст вершины
                        ├─► agent.Complete(messages, tools)     до 4 раундов tool-calls
                        │     apply_transition ─► training.ApplyChoice
                        │                          chat.ApplyDecision
                        │                          decisions.Create(+score) ─► событие decision
                        │                          концовка? ─► finish ─► UpdateUserScore
                        │     finish_chat      ─► finish с разбором от модели
                        └─ запись реплики агента ─► событие message
```

Клиент читает `message` / `decision` / `chat` / `error` из `GET /chats/{id}/events`.

### Особенности и решения

- **Чат не решает, сколько стоит выбор.** Веса приходят из YAML, чат стартует с нуля и копит
  дельты через `Chat.ApplyDecision`. Итог может быть отрицательным — осознанно: опасный выбор
  должен стоить дороже, чем «просто не заработал». Накопление, а не пересчёт по выборке решений,
  потому что список решений пагинирован — считать по нему значило бы посчитать по первой странице.
- **Решение и балл пишутся одним statement.** `CreateDecision` — data-modifying CTE, где
  `INSERT INTO chat_decisions` и `UPDATE chats` проходят вместе либо откатываются вместе.
  Балл здесь не производная величина, а состояние: разъехавшись один раз, он разъедется навсегда.
- **Закрытие идемпотентно.** `CloseChat` обновляет строку только пока `status = 'active'`
  и возвращает число затронутых строк. Начисление стоит ровно за успешным закрытием — повторное
  закрытие очков не добавит.
- **Один ход агента на чат.** `turnGate` (`usecase/chat/turngate.go`) пропускает по одному ходу
  на `chatID`. Без него два сообщения подряд давали два параллельных хода: оба успевали увидеть
  чат активным, и второй дописывал реплику мошенника уже после конца сценария.
- **Первая реплика детерминирована** — берётся текст стартовой вершины, без похода в LLM: текст
  уже написан автором, а пустой чат не даёт пользователю зацепки. Если сохранить её не удалось,
  чат удаляется — пустых чатов не остаётся.
- **Инструменты собираются под текущую вершину** (`usecase/chat/tools.go`). У модели их два:
  `apply_transition` с `transition_id` как **enum из переходов именно этой вершины** — поэтому
  «перепрыгнуть» сценарий она не может — и `finish_chat` с текстовым разбором. Описания переходов
  и примеры формулировок из YAML уходят в описание параметра.
- **Отказ модели не роняет ход.** Невалидные аргументы или отвергнутый движком переход
  возвращаются модели строкой `error: ...`, и она пробует ещё раз в пределах лимита раундов.
- **Сессия восстанавливается перед каждым переходом.** Сессии тренировки в памяти, чаты в БД;
  после рестарта `GetById` вернул бы `ErrSessionNotFound` и все живые чаты стали бы мёртвыми.
  `restoreSession` собирает сессию обратно из строки чата (`session_id`, `current_node_id`,
  `score`, статус) — репозиторий сессий при этом не менялся.
- **Пагинация всюду курсорная**, один тип `Cursor{Limit, AfterID}` на все списки, сортировка
  `id DESC`, потолок 100. По `id`, а не по `created_at`: курсору нужно уникальное монотонное поле.
  Выбрана не ради скорости, а ради отсутствия дублей при листании живого чата.
  **Цена и контракт для фронтенда: нумерованный пейджер невозможен**, только «показать ещё».
- **SSE — канал уведомлений, а не источник правды.** Публикация в шину неблокирующая: медленный
  подписчик теряет события, реплея нет. Состояние всегда перечитывается обычными ручками.
- **Авторизация потока — кукой.** Браузерный `EventSource` не умеет слать заголовок
  `Authorization`, поэтому `middleware.Auth` читает HttpOnly-куку `access_token` как fallback
  после `Bearer`. В query-параметр токен не выносим: он оседал бы в логах и истории браузера.
- **Проверка владельца везде**, включая SSE: `chat.UserID` сверяется с `userID` из контекста,
  иначе `403`. Существования чата недостаточно — `chatID` угадывается перебором.

### Контракты

**Требует от сценариев:** `GetById` (граф) и каталог для `GET /v1/scenarios`.
**Требует от training:** `Start`, `ApplyChoice`, репозиторий сессий — для регидратации.
**Требует от пользователей:** ровно `UpdateUserScore(ctx, userID, scoreDelta)` — узкий
consumer-side интерфейс `ScoreAwarder`. Совпал с существующим методом `usersusecase`, поэтому
адаптер не понадобился и слой users не менялся.
**Требует от auth:** `userID` в контексте.

**Отдаёт:** типы `Chat` / `Message` / `Decision` / `Event` / `Cursor`, три репозитория,
результат прохождения (`Resume`, `Score`) и HTTP-контракт.

**HTTP:** `POST /v1/chats`, `GET /v1/chats`, `GET /v1/chats/{chatID}`,
`POST /v1/chats/{chatID}/abandon`, `POST|GET /v1/chats/{chatID}/messages`,
`GET /v1/chats/{chatID}/decisions`, `GET /v1/chats/{chatID}/events` (SSE).

Коды: `400` — невалидный запрос или курсор, `401` — нет токена, `403` — чужой чат,
`404` — чат или сценарий не найден, `409` — чат закрыт либо у пользователя ещё нет профиля.

Полный контракт, тесты и техдолг — `backend/docs/chat.md`.

## Домен пользователей

`internal/domain/users` · `internal/usecase/users` · `internal/transport/rest/users` ·
`internal/repository/postgres/users` · `internal/auth` · `internal/middleware`

### Зачем он

Отвечать на два разных вопроса: «кто это» и «чего он добился». Первое — учётная запись и токены,
второе — игровой профиль, счёт и место в рейтинге.

### Модель

Сущности намеренно разведены по разным схемам БД:

| Схема | Таблица | Что хранит | Владелец |
|---|---|---|---|
| `auth` | `users` | `email`, `password_hash` (bcrypt), `created_at` | `internal/auth` |
| `users_schema` | `users` | `username`, `score`, `created_at`, `updated_at` | `internal/usecase/users` |
| `users_schema` | `user_progress` | `scenarios_completed`, `scams_detected`, `failed_attempts` | там же |

`id` профиля равен `id` учётной записи — отдельного маппинга нет, `POST /v1/users` вставляет
строку с уже известным `userID` из токена. Индекс `idx_users_score` покрывает лидерборд.

### Как работает

1. `POST /v1/auth/register` — валидация email и пароля, bcrypt-хеш, строка в `auth.users`.
   Профиль при этом **не создаётся**.
2. `POST /v1/auth/login` — сверка пароля, выдача пары токенов: access на 15 минут,
   refresh на 7 дней. Оба уходят HttpOnly-куками и в теле ответа.
3. `POST /v1/users` — создание игрового профиля с ником. Строка в `users_schema.users`
   и строка в `user_progress` заводятся одним запросом (CTE в `CreateUser`).
4. Дальше `middleware.Auth` на каждом запросе кладёт `userID` в контекст, а чат по завершении
   тренировки дёргает `UpdateUserScore`.

### Особенности и решения

- **Регистрация не создаёт профиль — и это видно снаружи.** Без `POST /v1/users` создание чата
  вернёт `409`. Разделение осознанное: учётка это одно, игровая личность с ником и счётом — другое.
- **Профиль и прогресс создаются атомарно.** `CreateUser` — CTE с двумя `INSERT`: профиля
  без строки прогресса не бывает.
- **Токенов два, и кука не декоративная.** Access живёт 15 минут, refresh — 7 дней.
  `middleware.Auth` читает `Bearer`, а куку `access_token` — как fallback: это единственный
  способ авторизовать браузерный SSE-поток чата.
- **Домен ничего не знает про чаты и сценарии.** Наружу он отдаёт
  `UpdateUserScore(ctx, userID, scoreDelta)` и принимает дельту; сколько начислить и когда —
  решает чат. Именно поэтому домен пережил появление чата без единой правки.
- **Счёт инкрементальный** — `score = score + delta` прямо в `UPDATE`, а не пересчёт по истории
  чатов. Идемпотентность обеспечивает чат своим `Close`, а не пользовательский домен.
- **Лидерборд — единственное место с `OFFSET`-пагинацией**, в отличие от курсорных списков чата:
  здесь нужен именно нумерованный пейджер и ранг. Сортировка `score DESC, id ASC` под индексом,
  `limit` по умолчанию 10 и не больше 100, ранг проставляется в юзкейсе как `offset + i + 1`.
  Общее число пользователей приходит отдельным `COUNT(*)`.
- **`user_progress` пока не заполняется** — известный техдолг. Счётчики остаются нулевыми:
  обновлять их — работа владельца домена, а чат туда не лезет. Данные для расчёта уже лежат
  в `chat_decisions`.
- **Секреты по умолчанию dev-овые.** `JWT_SECRET` имеет значение по умолчанию, куки идут
  с `Secure: false`. Перед публичным деплоем нужно поменять и то, и другое.

### Контракты

**Требует:** ничего от чата и сценариев.
**Отдаёт:** `UpdateUserScore` для начисления, `middleware.Auth` и `GetUserIDFromContext`
для всех остальных доменов, типы `User` / `UserProgress` / `Leaderboard`.

**HTTP:** `POST /v1/auth/register|login|refresh|validate` (без аутентификации),
`POST /v1/users`, `GET /v1/users/me`, `GET /v1/users/me/progress`,
`GET /v1/users/leaderboard?limit=&offset=`.

## Запуск

```bash
cp .env.example .env   # заполнить JWT_SECRET и DEEPSEEK_API_KEY
docker compose up --build
```

Поднимается три сервиса: `postgres`, `backend` и `frontend` (сборка Vite, отдача через
nginx). Наружу торчит только `frontend` — приложение на `http://localhost`, API под тем же
origin на `/api`, проверка живости — `GET /healthz`. Порт меняется через `FRONTEND_PORT`.

Postgres и backend доступны только внутри сети compose. Чтобы постучаться в них напрямую
при отладке, добавьте сервису `ports: ["8080:8080"]`.

Миграции накатываются на старте.

Обязательных переменных две — `JWT_SECRET` и `DEEPSEEK_API_KEY`, дефолтов у них нет.
У `POSTGRES_*`, `FRONTEND_PORT`, `DEEPSEEK_BASE_URL` и `DEEPSEEK_MODEL` значения по
умолчанию есть.

Фронтенд ходит в API относительным путём, поэтому CORS не участвует: nginx проксирует
`/api/` в backend, включая SSE (`proxy_buffering off`). В dev-режиме (`npm run dev`) то же
самое делает прокси Vite, backend при этом ждут на `http://localhost:8080` —
адрес переопределяется через `VITE_BACKEND_URL`.

## Проверка

```bash
API=http://localhost/api/v1

curl -X POST $API/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"trainee@example.com","password":"supersecret"}'

TOKEN=$(curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"trainee@example.com","password":"supersecret"}' \
  | sed -E 's/.*"access_token":"([^"]+)".*/\1/')

curl -X POST $API/users -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"username":"trainee"}'

curl $API/scenarios -H "Authorization: Bearer $TOKEN"

curl -X POST $API/chats -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"scenario_id":1}'
```

Профиль (`POST /users`) нужен до первого чата — без него создание чата вернёт `409`.

Дальше: `POST /chats/1/messages` отвечает `202` сразу, ответ агента приходит в SSE-поток
`GET /chats/1/events` событиями `message` / `decision` / `chat` / `error`.
