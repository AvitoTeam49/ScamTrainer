# Домен Chat — рамки работы

Документ фиксирует границы домена чатов: что входит в зону ответственности владельца домена,
какие контракты домен отдаёт наружу и требует от соседей, какие технические решения приняты.

Дополняет корневой `AGENT.MD` (стек и продуктовая цель), но не заменяет его.
Владелец домена — автор ветки `feature/chat`.

**Архитектура — монолит.** Один бинарь (`backend/cmd/app`), одна БД, одна папка миграций.
Домены Auth / Scenarios / Training / Chats / User — пакеты внутри `backend/internal/`,
а не отдельные сервисы. Границы ниже — организационные и компиляционные, а не сетевые.

**Текущее состояние.** Сквозной сценарий собран целиком: регистрация и вход по JWT,
каталог сценариев, создание чата с первой репликой, диалог с DeepSeek через tool-calls,
продвижение по графу сценария, завершение и начисление очков в профиль и лидерборд.
Всё поднимается через корневой `docker-compose.yml`.

## 1. Границы владения

### Моё — правим свободно(Mind)

- `backend/internal/domain/chat/**`, `backend/internal/usecase/chat/**`,
  `backend/internal/transport/rest/chat/**`, `backend/internal/repository/postgres/chat/**`
- `backend/internal/transport/rest/scenarios/**` — тонкий транспорт над чужим каталогом
- `backend/internal/eventbus/**`
- миграция таблиц чата `0003_chat_init.sql`

### Общее — правим только по согласованию, отдельным коммитом

- `backend/cmd/app/main.go` — точка сборки; домены туда только регистрируются
- `backend/internal/config/config.go`
- `backend/migrations/migrate.go`
- `backend/go.mod` / `go.sum`
- `backend/.golangci.yml`, `backend/Dockerfile`, `docker-compose.yml`

### Чужое — не трогаем

`backend/internal/scenario/**` (переехал в `internal/domain/scenario`), `internal/training/**`,
`internal/auth/**`, `internal/middleware/**`, `internal/domain/users/**` и остальной слой users.

Правка на той стороне описывается требованием в разделе 2 и передаётся владельцу домена.
Единственное исключение, сделанное по согласованию, — проводка auth: метод `(*API).Register`
и приём `jwtSecret` в `NewAuthService`. Логика регистрации, входа и валидации токенов не тронута.

При слиянии с `origin/main` чужой код правился только механически, по границам пакетов:
путь импорта `internal/scenario` → алиас на `internal/domain/scenario`, квалификация типов
в тестах. Имена и сигнатуры сохранены как есть — в частности `GetById`, а не `GetByID`.

## 2. Контракты с соседними доменами

Соседние домены вызываются **напрямую, как Go-код** — никакого HTTP, gRPC или очередей
между доменами внутри монолита. Конкретные реализации связываются в `cmd/app/main.go`.

**Правило зависимостей:** chat работает через интерфейсы, объявленные на стороне потребителя
(consumer-side), либо через интерфейсы соседа, если сосед их уже отдаёт.

### Чат требует от Scenarios

- `scenariodomain.ScenarioRepository` — `GetById(ctx, id int) (*Scenario, error)`.
  Даёт граф сценария: `StartNodeID`, вершины, переходы, промпты.
- `scenariodomain.ScenarioCatalog` — `List` / `ListByDifficulty`. Нужен ручке
  `GET /v1/scenarios`: без каталога клиент не знает валидный `scenario_id`.

Идентификатор сценария — `int`, задаётся полем `id` в самом YAML. Отдельного маппинга
между числовым и строковым id больше нет.

### Чат требует от Training

- `training.TrainingService.Start(ctx, userID, scenarioID)` — создать сессию, отдать
  стартовую вершину.
- `training.TrainingService.ApplyChoice(ctx, sessionID, transitionID)` — продвинуть сессию
  по графу, вернуть `Decision` и признак завершения.
- `training.SessionRepository` — нужен чату напрямую для регидратации (раздел 3).

Чат не ходит в `scenario.Engine` сам: движок принадлежит Training, чат хранит только
`session_id` и зеркалит результат в свои таблицы.

### Чат требует от User

Начисление очков через узкий consumer-side интерфейс `chatusecase.ScoreAwarder`:

```go
UpdateUserScore(ctx context.Context, userID int64, scoreDelta int) error
```

Домен пользователя про чаты и сценарии не знает и знать не должен: он принимает дельту,
а сколько начислить и когда — решает чат. Интерфейс совпадает с уже существующим методом
`usersusecase`, поэтому адаптер не нужен и слой users не менялся.

### Чат требует от Auth

`middleware.Auth` кладёт `userID` в контекст, чат достаёт его через
`middleware.GetUserIDFromContext`. Собственной идентификации у чата нет.

### Чат отдаёт наружу

- типы домена: `chatdomain.Chat`, `ChatStatus`, `Message`, `SenderType`, `Decision`,
  `Event`, `Cursor`;
- `ChatRepository` — `GetByID` / `ListByUserID` / `Create` / `Close` / `Delete`.
  `Close` пишет любой терминальный статус — `finished` или `abandoned`;
- `MessageRepository` — `ListByChatID` / `Create`;
- `DecisionRepository` — `ListByChatID` / `Create`. `Create` принимает вторым аргументом
  уже пересчитанный балл чата: `Create(ctx, decision *Decision, score int64) error`;
- результат прохождения: поля `Resume string` и `Score int64` в `Chat`.

## 3. Технические решения домена

**Выбор БД — PostgreSQL.** Чаты, сообщения, решения и пользователи — строго связанные данные:
нужны внешние ключи, упорядоченная выборка истории по `chat_id` и запись решения вместе
с обновлением балла. Redis в проекте не используется: горячая история умещается в один
keyset-запрос, а вводить второе хранилище ради этого незачем.

**Хранение.** Таблицы заведены в `0003_chat_init.sql`:

- `chats` — `id`, `user_id` (FK на `users_schema.users`), `scenario_id`, `session_id`,
  `title`, `status`, `resume`, `score`, `current_node_id`, `created_at`, `finished_at`
- `messages` — `id`, `chat_id`, `sender_type`, `content`, `created_at`
- `chat_decisions` — `id`, `chat_id`, `node_id`, `transition_id`, `target_node_id`,
  `score_delta`, `feedback`, `created_at`

`sender_type` — `agent` / `user`, `status` — `active` / `finished` / `abandoned`.

**Оценка идёт от сценария, а не от таблицы весов в коде.** Вес переходу задаёт автор
сценария полем `score_delta` в YAML. Чат стартует с нуля и накапливает дельты через
`Chat.ApplyDecision`; итог может быть отрицательным — это осознанно, опасный выбор должен
стоить дороже, чем «просто не заработал».

Накопление выбрано вместо расчёта по полной выборке решений, потому что список решений
пагинирован: считать балл по нему значило бы посчитать по первой странице.

**Запись решения и обновление балла идут одним statement.** Балл — не производная величина,
а состояние: если решение запишется, а `chats.score` не обновится, счётчик разъедется
навсегда. Запрос `CreateDecision` — data-modifying CTE, где `INSERT INTO chat_decisions`
и `UPDATE chats` проходят вместе либо откатываются вместе. Явная `pgx.Tx` не нужна, поэтому
адаптер работает через `DBTX` и остаётся совместим с внешней транзакцией.

**Закрытие чата идемпотентно.** `CloseChat` обновляет строку только пока `status = 'active'`
и возвращает число затронутых строк. Начисление стоит ровно за успешным `Close`, поэтому
повторное закрытие очков не добавляет.

**Один ход агента на чат.** Ход запускается горутиной на каждое сообщение, поэтому два
сообщения подряд давали два параллельных хода: оба успевали увидеть чат активным, и второй
дописывал реплику мошенника уже после завершения сценария. `turnGate` (`usecase/chat/turngate.go`)
пропускает по одному ходу на `chatID`, и проверка `chat.IsActive()` снова осмысленна —
второй ход читает чат уже закрытым и выходит. Ворота в памяти процесса, как шина событий
и сессии тренировки.

**Отказ от тренировки.** `POST /v1/chats/{id}/abandon` переводит чат в `abandoned` через тот же
`Close`. Очки не начисляются: сценарий не пройден. Накопленный счёт чата остаётся для истории.
Если в этот момент шёл ход агента, он обнаружит закрытый чат и отдаст в SSE `error`
с причиной `chat is already finished` — состояние при этом корректное.

**Начисление не может уронить ход.** К моменту начисления чат уже завершён и сохранён,
поэтому ошибка `ScoreAwarder` логируется и не пробрасывается.

**Сессии тренировки живут в памяти, чаты — в БД.** После рестарта `sessions.GetById` вернёт
`ErrSessionNotFound`, и все живые чаты стали бы мёртвыми. Поэтому перед каждым переходом чат
восстанавливает сессию из собственной строки (`restoreSession` / `sessionFrom`): `session_id`,
`current_node_id`, `score` и статус — всё, что нужно движку. Репозиторий сессий при этом
не менялся.

**Первая реплика детерминирована.** При создании чата сохраняется сообщение с текстом
стартовой вершины сценария, без похода в LLM: текст уже написан автором сценария, а пустой
чат не даёт пользователю зацепки.

**Пагинация.** Все списки курсорные, тип один на все — `Cursor{Limit, AfterID}`.

- Сортировка — `id DESC`, новые первыми. По `id`, а не по `created_at`: курсору нужно
  уникальное монотонное поле, две записи в одну миллисекунду сломали бы выборку.
- `AfterID = 0` — начало списка. Пустой курсор по сообщениям даёт «последние N реплик» —
  то, что нужно DeepSeek; вызывающий разворачивает срез в хронологию сам.
- Признак «есть ещё» — заполненное `next_after_id`, оно ставится только на полной странице.
- Потолок `MaxCursorLimit = 100`. `Cursor.Validate()` возвращает `ErrInvalidCursor`
  и ничего не исправляет молча: дефолты подставляет транспорт.

Курсор выбран не ради производительности — глубины здесь нет. Причины: один тип на все списки
и отсутствие дублей при листании живого чата, куда во время листания приходят новые сообщения.

Цена решения, и это контракт для фронтенда: **нумерованный пейджер невозможен** —
только «показать ещё» или бесконечная прокрутка. **Сортировку списка чатов сменить нельзя** —
например, «по баллу» потребует возврата к `OFFSET`.

**События и SSE.** `internal/eventbus` — in-process pub/sub с fan-out по `chatID`. Отправка
сообщения отвечает `202` сразу и запускает ход агента в горутине, результат приходит клиенту
событиями `message` / `decision` / `chat` / `error`.

Публикация неблокирующая: медленный подписчик теряет события, реплея нет. Это осознанный
размен — SSE здесь канал уведомлений, а не источник правды; состояние всегда можно
перечитать через `GET /v1/chats/{id}` и списки.

**Авторизация SSE — кукой.** Браузерный `EventSource` не умеет отправлять заголовок
`Authorization`, поэтому на входе рядом с refresh выставляется HttpOnly-кука `access_token`,
а `middleware.Auth` читает её как fallback после `Bearer`. Токен в query-параметр не выносим:
он оседал бы в логах доступа и истории браузера.

**Проверка владельца.** Все ручки чата, включая SSE, сверяют `chat.UserID` с `userID`
из контекста и отвечают `403`. Существования чата недостаточно: `chatID` угадывается перебором.

**DeepSeek.** Клиент и цикл обработки ответов агента, включая tool-calls, живут за интерфейсом
`agent.Agent` (`internal/agent/agent.go`) — чтобы подменяться моком в тестах.

Контракт агента лежит не в `domain`: `Role`, `Message`, `ToolCall`, `ToolDefinition` — форма
протокола OpenAI, а не язык предметной области, и ни `Chat`, ни `Message`, ни `Decision`
их не используют. Поэтому протокол общения с LLM живёт в `internal/agent` рядом с единственной
реализацией `agent/deepseek`, а `domain` остаётся про чаты, реплики и решения.

Клиент — свой, на stdlib (`net/http` + `encoding/json`). Официального Go-SDK у DeepSeek нет,
API OpenAI-совместимый, нужен ровно один эндпоинт `POST /chat/completions` со `stream: false`,
поэтому зависимость не заводим. Набор инструментов собирается под текущую вершину графа
(`usecase/chat/tools.go`): `transition_id` — enum из переходов именно этой вершины, поэтому
модель не может «перепрыгнуть» сценарий.

## 4. HTTP-контракт

Всё под `HTTP_PREFIX` (по умолчанию `/api`). `GET /healthz` — вне префикса.

| Метод | Путь | Аутентификация |
|---|---|---|
| POST | `/v1/auth/register`, `/v1/auth/login`, `/v1/auth/refresh`, `/v1/auth/validate` | нет |
| GET | `/v1/scenarios` | да |
| POST | `/v1/chats` | да |
| GET | `/v1/chats` | да |
| GET | `/v1/chats/{chatID}` | да |
| POST | `/v1/chats/{chatID}/abandon` | да |
| POST | `/v1/chats/{chatID}/messages` | да |
| GET | `/v1/chats/{chatID}/messages`, `/decisions` | да |
| GET | `/v1/chats/{chatID}/events` (SSE) | да, допускается кука |
| POST | `/v1/users` | да |
| GET | `/v1/users/me`, `/me/progress`, `/leaderboard` | да |

Коды ошибок чата: `400` — невалидный запрос или курсор, `401` — нет токена,
`403` — чужой чат, `404` — чат или сценарий не найден, `409` — чат уже закрыт либо
у пользователя ещё нет профиля в users (`POST /v1/users` не вызывался).

`GET /healthz` пингует пул Postgres и отдаёт `503`, если база недоступна.

## 5. Тесты

**Уровень — юзкейс.** Тесты домена лежат в `internal/usecase/chat/chat_test.go` (25 тестов)
и объявлены в самом пакете `chatusecase`, а не в `_test`-пакете: часть проверок смотрит на
внутренние детали вроде `defaultHistoryLimit`. Все внешние зависимости сервиса подменены
фейками, поэтому прогон не ходит ни в базу, ни в сеть, ни в LLM.

**Фейки моделируют контракты, а не возвращают заглушки.** Это главное, что делает тесты
осмысленными, и это же нужно поддерживать при правках:

- `fakeChatRepository.Close` возвращает `true` только на первый вызов — ровно то, что
  в проде обеспечивает `AND status = 'active'` в `CloseChat`. Без этого тесты на двойное
  начисление и сериализацию ходов ничего бы не проверяли.
- `fakeMessageRepository.ListByChatID` вызывает `Cursor.Validate()`, как все три настоящих
  репозитория. Поэтому тест на зажим `HistoryLimit` красный, если зажим убрать: курсор
  со `Limit > MaxCursorLimit` упрётся в `ErrInvalidCursor`.
- `fakeAgent` проигрывает заранее записанный список ответов, включая tool-calls, — раунды
  общения с моделью воспроизводятся детерминированно.
- Репозиторий сессий тренировки берётся настоящий (`training.InMemorySessionRepository`):
  он и в проде в памяти, подменять нечего.

Фикстура — `newFixture(t, currentNodeID)`; если нужен сервис с непустыми `Options`, есть
`newFixtureWith(t, currentNodeID, options)`.

**Что закрыто.** Продвижение по графу и знак балла, начисление ровно один раз, сериализация
параллельных ходов через `turnGate`, регидратация потерянной сессии, отказ от тренировки,
откат чата при неудачной первой реплике, отклонение чужого чата и чата на вершине-концовке,
tool-call без текста, enum переходов от текущей вершины, лимиты длины сообщения и заголовка
(считаются рунами, не байтами), зажим и дефолт лимита истории, отвязка снапшота в `ChatEvent`
от живого чата.

Соседние пакеты покрыты своими тестами: `eventbus` (fan-out, отписка, медленный подписчик),
`training`, `domain/scenario` (движок и валидация графа), `repository/yaml/scenario`.

**Что не покрыто и почему.** Транспортный слой (`transport/rest/chat`) — тестов нет.
SQL-репозитории (`repository/postgres/chat`) юнит-тестами не проверяются в принципе: нужна
живая база. Изменения в `queries.sql` проверяются вручную — поднять Postgres, накатить
миграции, прогнать запрос в обеих ветках (активный чат и уже закрытый). Так проверялась
идемпотентность `CreateDecision`.

**Прогон.**

```bash
cd backend
go test ./... -count=1              # -count=1 отключает кэш результатов
go test ./... -cover
go test ./internal/usecase/chat ./internal/eventbus ./internal/training -race
```

`-race` требует cgo. Если локальный тулчейн собран под `GOARCH=386`, детектор не
поддерживается — нужен `GOARCH=amd64 CGO_ENABLED=1` и 64-битный gcc.

`gofmt -l` на этом репозитории шумит: файлы с CRLF он считает неотформатированными.
Чтобы отличить перевод строки от настоящей проблемы: `tr -d '\r' < файл | gofmt -d`.

## 6. Принятый технический долг

- **Раскладка неоднородна**: `internal/auth`, `internal/middleware`, `internal/training`
  плоские, `chat` и `users` — слоевые. Следствие решения не переписывать чужие пакеты.
- **Сессии тренировки in-memory.** Переживают рестарт только за счёт регидратации из `chats`.
  Инстанс один; горизонтальное масштабирование потребует Postgres-репозитория сессий.
- **Event bus in-process.** Вторая причина, почему инстанс пока один. Для нескольких реплик
  нужен внешний pub/sub.
- **Начисление очков и завершение чата — не в одной транзакции.** Идемпотентность закрывает
  двойное начисление, но не разрыв между `CloseChat` и `UpdateUserScore`.
- **Ворота ходов и откат чата — компенсации, а не транзакции.** `turnGate` защищает только
  внутри процесса, а упавшая первая реплика откатывается ручным `Delete`, который тоже
  может не пройти.
- **`user_progress` не заполняется.** Счётчики `scenarios_completed` / `scams_detected` /
  `failed_attempts` остаются нулевыми: обновлять их — работа владельца домена users, чат
  туда не лезет. Данные для расчёта лежат в `chat_decisions`.
- **Секреты в compose дефолтные.** `JWT_SECRET` имеет dev-значение, куки идут с `Secure: false`.
  Перед публичным деплоем и то, и другое нужно поменять.
